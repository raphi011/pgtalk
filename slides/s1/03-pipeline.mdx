<Note appearAt={1} hideAt={2}>

**Grammar, and nothing else.** It knows that `SELECT` must be followed by a
list of expressions. It does not know what a `customer` is.

`SELECT FRUM customers` dies here, at a character position.
`SELECT nope FROM customers` sails straight through.

</Note>

<Note appearAt={2} hideAt={3}>

**Meaning.** Every name is resolved against the catalog: `customers` becomes
an OID, `email` becomes an attribute number, `=` becomes one specific function
for one specific pair of types.

Because it has the catalog open, this is the stage that can tell you what you
probably meant.

</Note>

<Note appearAt={3} hideAt={4}>

**Expansion.** A query against a view is replaced by the view's definition.
Rules and row-level security policies are applied here too.

Most queries pass through untouched — but a view of a view of a view arrives
at the planner much larger than you wrote it.

</Note>

<Note appearAt={4} hideAt={5}>

**Choice.** It enumerates equivalent ways to answer the query — which index,
which join order, which join algorithm — prices each one using statistics and
a handful of cost constants, and keeps the cheapest.

It never reads a single row of your data. Every number it produces is a
prediction.

</Note>

<Note appearAt={5} hideAt={6}>

**Work.** It walks the chosen plan as a tree of iterators, each node asking
its children for one more row.

This is the only stage that touches your data, and the only one
`EXPLAIN ANALYZE` can put a clock on.

</Note>

<Note appearAt={6}>

**One of these five guesses.** The parser, analyzer, rewriter and executor are
deterministic: the same input gives the same output, every time.

The planner is the one that can be right about everything it knows and still
choose a plan that takes four minutes.

</Note>
